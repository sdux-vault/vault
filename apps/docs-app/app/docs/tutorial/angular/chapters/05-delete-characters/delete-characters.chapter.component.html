Chapter 5: Delete Characters

This chapter adds delete behavior without moving collection ownership, delete rules, or confirmation logic into the template. The workflow now supports destructive updates through the same service-owned boundary.

Keep the same split in place: the service is still the only place that updates committed Feature State, while the component owns local selection, confirmation, editor, and feedback state. Keeping that line clear makes delete behavior easier to follow and easier to maintain.

Make destructive changes explicit, confirmable, and state-safe.

Deletion changes more than a button label: it removes a record from the feature's committed collection and can be difficult to undo. This chapter adds a deliberate confirmation point while keeping the actual removal on the same service-owned pipeline used for every other mutation.

Why this boundary matters

The component coordinates selection, confirmation, and feedback, but it never edits the committed collection directly. The service owns the destructive policy and routes a new collection through replaceState(), so the operation remains observable, immutable, and consistent with the rest of the Feature State lifecycle.

Use this structure for

  • removing a saved item after an explicit confirmation
  • revoking an assignment or removing access to a record
  • deleting a draft while preserving a clear cancellation path

By the end of this chapter

You will have a pending-delete state, a cancelable confirmation flow, and a service-owned removal method that removes the selected character by identity while preserving every other committed record.

Chapter 5 Starting Point and Change Map

Start with the completed Chapter 4 project. Add one service removal method, then add component-local pending-delete state, request/cancel/confirm handlers, confirmation markup, and focused tests. The registered append merge remains available for create; deletion submits a complete next collection through replaceState().

What “Destructive” Means Here

The array transformation is immutable, but the user-visible record is intentionally removed from committed State. This browser-only tutorial does not implement server authorization, durable deletion, undo, optimistic rollback, or audit logging. Add those controls at the real persistence boundary in production.

Step 1: Configure Array By Id Merge Behavior
↑ top

Before the service can delete a character correctly, the registered needs index-style merge semantics. In the previous chapter, it used append-style merge semantics for adding new characters.

Now we need to switch to index-style merge semantics to handle deletions correctly.

To change that Merge-stage behavior, install the package and register withArrayByIdMergeBehavior in app.config.ts. This makes mergeState() use an index-style merge to delete, add and edit a character.

  2. Open app.config.ts

  4. Pass [withArrayByIdMergeBehavior] as the behavior list for provide().

Why This Behavior Is Required
  • mergeState() is the right API for adding a new record to an existing collection.
  • Without array-by-id merge behavior, the incoming one-item array would replace the entire current collection.
  • With withArrayByIdMergeBehavior, that same one-item array is appended immutably to the committed collection.
  • This keeps add and edit distinct: create uses mergeState() to append, while update will use replaceState() to swap one existing character by identity.
Avoid Manual Array Merging

You could build the next collection manually with a spread expression such as [...currentCharacters, newCharacter], but that is the wrong approach for this tutorial.

The spread operator itself does not mutate the array. The anti-pattern is pushing merge policy into the service instead of configuring it in the pipeline. In , append behavior belongs to the Merge stage so mergeState() can apply that rule consistently instead of forcing application code to reimplement it by hand.

Unknown or Stale IDs

removeCharacter() always submits a replaceState() factory. When the ID is absent, the factory filters the latest collection into an equivalent new array; the example does not treat that as an error or create a record. The service spec verifies the resulting value, not an emission-count guarantee. In a multi-writer application, revalidate the pending record at confirmation time. Any success feedback shown for a stale ID is a tutorial limitation, not an authoritative server acknowledgment; report the stale deletion instead of claiming success.

Delete Outcome Contract
Action FeatureCell request Expected result
Cancel delete No request Clears only the component's delete candidate. The collection and selection remain unchanged.
Confirm a known ID replaceState() Removes the matching record, clears selection and the form, and returns the editor to create mode. Every nonmatching record is retained.
Confirm a stale ID replaceState() Leaves the collection equivalent. This tutorial makes no promise about subscriber emission for equivalent array values.
What to Look For
  • Cancel preserves the record; confirm removes only that identity and clears stale local selection.
  • The component coordinates confirmation while the service owns replacement.
  • Save this checkpoint for Chapter 5 and reload it after testing terminal destruction.
