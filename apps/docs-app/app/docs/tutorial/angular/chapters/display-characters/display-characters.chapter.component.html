Add interaction without moving ownership.

A fixed detail view proves that managed State can reach the UI. A useful application lets people decide which record to inspect. This chapter adds that choice without turning a short-lived UI decision into shared Feature State or duplicating the collection in the component.

Why this boundary matters

The character collection remains the service-owned, committed source of truth. A selected id only describes what this component is showing right now. Keeping those responsibilities separate prevents temporary navigation choices from coupling other consumers to this one view.

Use this structure for

  • a master-detail page for customers, products, or records
  • a picker whose choice affects only the current view
  • an interactive read path that will later support editing

By the end of this chapter

You will have a dropdown backed by the committed character collection, a component-local selection Signal, and a reactive detail panel that follows the selected record while the service continues to own the .

Chapter 2 Starting Point and Decision

Start with the completed Chapter 1 project. This chapter changes only example.component.ts, example.component.html, and the component spec. Registration, bootstrap, seed data, and the service remain unchanged.

Keep Selection Local When

The selected ID describes only what this component is displaying. Promote selection to shared Feature State only when another consumer, a route, persistence, or cross-tab behavior must observe the same selection. Local state is the smaller and safer choice for this master-detail view.

Step 11: Add a Dropdown
↑ top

This step upgrades the initial read path from showing the first committed record automatically to letting the user choose which committed record to inspect. The Feature registration, service-owned , and managed collection stay the same; only the UI-facing selection logic changes.

Assume the Angular mechanics are already familiar. Here, keep Feature State in the service, keep selection state in the component, and derive the displayed record from the latest service-owned collection. To do that, replace the single displayed-character computed Signal with a read-only character collection, a selectedCharacterId Signal, a computed lookup for the selected record, and a small selection handler. In the template, add a select element that lists the registered characters and keep the detail panel bound to computed controller state instead of reaching into directly. The matching verification belongs in this same step: the updated component spec should prove the controller starts empty, accepts a valid selection, ignores unknown ids, and renders the selected record without moving ownership out of the service.

Reactive Lookup

The selected character depends on two values: the latest committed collection from the service and the component-local selected ID. When either changes, the computed lookup runs again. A known ID produces its record; an empty or unknown ID produces no selected record and the template renders the empty state.

Make the Change
  1. In example.component.ts, replace the single-record computed value with characters, a computed read of this.#exampleService.state.value() ?? [].
  2. Add selectedCharacterId as a local Signal initialized to null. Add selectedCharacter as a computed lookup that returns the matching collection record or null.
  3. Add selectCharacter(value: string). Convert the dropdown value with Number(value), set the Signal only when that ID exists in characters(), and otherwise leave the current local selection unchanged.
  4. In example.component.html, render one option per characters() entry and pass the selected value to selectCharacter(). Render the details panel only when selectedCharacter() returns a record; otherwise render the empty guidance.
  5. Start with no selection, choose Leia, and confirm the detail panel shows Leia. Submit an unknown value in the component spec and confirm no record is manufactured and Feature State remains unchanged.
What to Look For
  • The service still owns the and does not change for this UI enhancement.
  • The selection Signal is presentation state owned by the component, not Feature State owned by the service.
  • The template continues to render computed, display-ready values instead of reading APIs directly.
  • The spec verifies the new UI behavior without changing the -owned Feature State contract.

Step 12: Complete Dropdown Tutorial
↑ top

The dropdown tutorial is complete once the page starts with no selected character, lists the registered collection in the picker, and updates the detail panel when the selection changes. The boundary has not moved: the service still owns the and the component still owns only UI selection state.

This is the smallest useful expansion of the initial tutorial: the application moves from one fixed read path to one user-directed read path without changing registration, service ownership, or application bootstrap structure. What changed is the proof that the same service-owned State can now support both an initial empty state and a selected-record view.
