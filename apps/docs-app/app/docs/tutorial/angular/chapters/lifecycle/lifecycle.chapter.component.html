Step 18: Persist Null and Reset State
↑ top

This chapter focuses on lifecycle clearing instead of record mutation. You will clear the Feature in two distinct ways while keeping the same service-owned boundary intact.

Pair these two operations deliberately. Persisting null is a normal replaceState() update: you are storing an intentional value, and the Feature remains alive for future work. Calling reset() is different: it clears the current snapshot back to the neutral runtime state without finalizing the Feature. The service should own both lifecycle APIs, and the component should respond by clearing only its temporary UI state.

Take Action
  1. Open example.service.ts and add persistNullState() plus resetState().
  2. Use replaceState() for the intentional null write, and use reset() for the neutral-state clear.
  3. Update the service spec so the chapter proves null and undefined are not the same lifecycle outcome.
What to Look For
  • Persisting null is still just state replacement, so it belongs in the same service-owned write boundary as create, update, and delete.
  • reset() does not store a replacement value. It clears the current snapshot and leaves the ready for later updates.
  • The component should clear selection, form, and confirmation Signals after either lifecycle action, but it still should not call APIs directly.
  • Use this step to distinguish an intentional empty value from a runtime reset before you move to permanent teardown.

Step 19: Finalize with destroy()
↑ top

The last lifecycle step is intentionally different from everything before it. Calling destroy() does not clear the current value for future reuse. It permanently finalizes the , ends its runtime lifecycle, and turns every later interaction into an invalid operation.

That means the component needs one more responsibility: when the service destroys the Feature, the UI must stop pretending the collection is still interactive. Clear local editor state, disable later actions, and render an explicit lifecycle message so you can see finalization instead of a silent failure. The architectural line still does not move: the service owns destroy(), and the component owns the visual response to that final state.

Take Action
  1. Update example.component.ts to add lifecycle action handlers for persist-null, reset, and destroy.
  2. Update example.component.html to add the lifecycle control bar, snapshot summary, and destroyed-state messaging.
  3. Verify that the UI resets safely for null and reset(), then disables later interaction after destroy().
Lifecycle Flow Summary
  • The component now shows three lifecycle outcomes: intentional null persistence, runtime reset, and permanent teardown.
  • The template now exposes the raw lifecycle result so you can see the difference between null and undefined instead of inferring it.
  • After destroy(), the UI stops offering the earlier CRUD interactions because the Feature lifecycle is complete.
