Replay Global Error Controller Flow
↑ top

This diagram illustrates how the Replay Global Error Controller participates in pipeline execution when a global Vault error is present. Controllers do not execute within a pipeline stage and do not observe state directly. Instead, they operate through the Conductor, responding to execution attempt messages and issuing votes that determine whether a pipeline execution may proceed, be denied, or be replayed.

The flow highlights the role of the VaultErrorService as the authoritative source of global error state. When a global error is active, the service emits an error signal that influences both interceptor gating and controller arbitration. While the paired interceptor blocks new pipeline admission, the Replay Global Error controller evaluates execution attempts associated with the current trace and issues denial votes while the error remains active.

The Decision Engine acts as the centralized arbitration point, collecting controller votes and applying them deterministically. When the global error state changes—such as when VaultErrorService.clear() is invoked—the controller may request a revote for previously denied attempts, allowing execution to resume under the updated conditions.

This design cleanly separates responsibilities: the VaultErrorService signals global error lifecycle events, the interceptor controls pipeline admission, and the controller governs execution replay and retry behavior through formal arbitration rather than side effects or implicit retries.

Stepwise Controller Flow
↑ top

This diagram illustrates how the Stepwise Controller coordinates policy-driven execution control when a Stepwise behavior emits a decision request. Unlike standard pipeline stages, Stepwise does not resolve synchronously. Instead, execution is intentionally paused while awaiting an explicit external decision.

When a Stepwise behavior is invoked at the Filter, Reducer, or Resolve stage, it emits a decision request rather than returning a value. The pipeline immediately suspends execution for the current trace and forwards the request to the Stepwise Controller through the Stepwise bus.

The Stepwise Controller serializes all incoming requests using a FIFO queue, ensuring that only one Stepwise decision is active at any given time. This guarantees deterministic execution order and prevents overlapping or ambiguous policy resolution when multiple Stepwise behaviors are configured.

While awaiting a response, no downstream pipeline stages execute, no snapshots are committed, and no additional updates are admitted for the affected execution trace. The pipeline remains fully paused until an external system — such as user input, developer tooling, or an automated policy engine — emits a corresponding decision.

Once a response is received, the controller translates it into a canonical pipeline control signal and resumes execution according to the decision:

  • continue — resume pipeline execution at the appropriate downstream stage
  • block — suppress the current update with no state change
  • clear — clear existing state and terminate the current update

After resolving the active request, the controller advances its internal queue and processes the next pending Stepwise request, if any. This design ensures that policy enforcement remains explicit, serialized, and fully observable without compromising pipeline safety or determinism.

Behavior & Add-on Diagrams

Interceptor Behavior
↑ top

Interceptors execute before pipeline admission and may halt execution entirely. This diagram shows how pre-processing and admission control interact with the rest of the pipeline.

Global Error Pause Flow
↑ top

This diagram illustrates how the Global Error Pause behavior intercepts incoming pipeline candidates when a global Vault error is active. The behavior operates before pipeline admission and determines whether an incoming candidate is allowed to enter the pipeline.

When a global error is present, incoming candidates are blocked at the interceptor boundary and do not proceed into downstream pipeline stages. Blocked candidates are discarded and are not queued or replayed automatically when the global error is cleared.

Once the global error signal is resolved, normal pipeline admission resumes for newly incoming candidates. Replay behavior is not part of this flow and must be provided explicitly by a controller if required.

Operator Flow
↑ top

This diagram illustrates the Operator stage in isolation, showing how resolved and merged pipeline values are evaluated before entering filtering, reduction, and tap stages. Operators receive the fully resolved pipeline value and determine whether that value should continue through the remaining pipeline stages.

An operator may forward the value unchanged, forward a modified value, or terminate the current pipeline execution by returning VAULT_NOOP. When a noop is returned, downstream stages are skipped and no snapshot is emitted for that execution. Future pipeline executions are unaffected and will re-enter the Operator stage normally.

State Flow
↑ top

This diagram illustrates how the State Stage emits the finalized state snapshot after pipeline execution completes. The committed snapshot is exposed through the synchronous .state surface (represented as a signal in Angular) and emitted through the reactive .state$ observable.

After the snapshot is committed and exposed through .state and .state$, optional emit-state callbacks may observe the same immutable snapshot for legacy, diagnostic, or compatibility handling. Emit-state callbacks are observational and do not influence state commitment or pipeline execution.

Encryption occurs after state computation and before persistence. This diagram highlights how encrypted storage remains a side effect while emitted state snapshots stay plaintext.

Decrypt Lifecycle
↑ top

Decryption occurs during FeatureCell initialization when persisted encrypted state is restored. This diagram shows how encrypted data is converted back into an initial plaintext snapshot.

Persist Lifecycle
↑ top

Persistence occurs after state computation and any optional encryption has completed. This diagram illustrates how persist behaviors observe the finalized, committed FeatureCell state and write it to external storage as a side effect, without influencing emitted state snapshots or pipeline control flow.

Persist behaviors operate exclusively on the final pipeline output. They do not transform state, do not emit snapshots, and do not participate in decision-making. Persisted storage is updated only after state has been fully reduced and committed.

State Cache Flow
↑ top

State cache operations introduce an identifier-based lookup surface that coordinates cache hits, cache misses, refresh resolution, and fan-out handling through the FeatureCell pipeline. This diagram illustrates how cached entities are resolved, refreshed, and delivered without bypassing pipeline execution.

Lookup Flow
↑ top

Lookup operations provide identifier-based entity resolution without time-based expiration. This diagram shows how lookup requests coordinate hits, lookup-miss resolution, and concurrent fan-out through the FeatureCell pipeline before delivering a resolved entity to the consumer.

Query Flow
↑ top

Query operations provide synchronous identifier-based access to entities that already exist in finalized FeatureCell state. The query behavior maintains an internal entity index derived from committed state emissions and resolves requests directly from this index without triggering pipeline execution.

This diagram illustrates how finalized state emissions populate the query cache and how query requests resolve immediately from locally indexed entities while preserving the FeatureCell pipeline as the authoritative source of truth.
