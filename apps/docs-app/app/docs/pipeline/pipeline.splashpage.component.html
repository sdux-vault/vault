The Pipeline

The pipeline is the ordered sequence of stages through which every FeatureCell update is evaluated. Each stage has a defined responsibility, such as governing execution timing, transforming state, applying rules, and producing a finalized snapshot.

This page provides a high-level conceptual overview of the pipeline. All other documentation pages build upon this structure. Understanding these layers establishes the foundational mental model for .

Pipeline behavior is deterministic and ordered. A FeatureCell assembles its pipeline from an explicit set of enabled behaviors. Only behaviors that are explicitly configured are included in the pipeline. Each enabled behavior is placed into its designated stage according to its contract.

A small set of core stages is always present in every FeatureCell. These stages ensure that incoming updates are ordered, normalized, and produce a valid, immutable state snapshot. All other stages are optional and exist only when corresponding behaviors are enabled.

The behaviors considered “core” and guaranteed in every FeatureCell:

  • Queue (execution ordering)
  • Resolve (normalization of incoming values)
  • Default Merge (array replace)
  • State (emission of the final StateSnapshotShape)

Optional pipeline stages act as modular extensions layered on top of the core pipeline. They do not alter the guarantees of the core stages and are evaluated only when explicitly configured.

1. Policy Layer

The Policy Layer governs execution authority for pipeline attempts. It operates outside of value transformation stages and determines whether, when, and how a pipeline execution may proceed.

Policy logic is implemented through Controllers, which issue authoritative execution decisions. These decisions are evaluated by the Decision Engine and enforced by the Conductor. Controllers do not transform state, derive values, or emit snapshots. Their responsibility is limited to execution control.

The Policy Layer executes at defined lifecycle boundaries—most notably during attempt admission and failure handling. Every pipeline attempt must pass through policy evaluation before work begins.

Responsibilities

  • Authorize or deny pipeline execution attempts
  • Pause execution until required conditions are satisfied
  • Abort execution attempts deterministically
  • Trigger controlled retry behavior following failures
  • Coordinate multiple controller decisions into a single enforced outcome

Policy Decisions

Each controller issues a control decision indicating how the pipeline should respond to the current attempt. Decisions are evaluated collectively and resolved into a single authoritative outcome.

  • Complete — the attempt is permitted to proceed
  • Deny — the attempt is paused or blocked until conditions change
  • Abort — the attempt is terminated and removed from execution

Why Policy Is Not a Behavior

  • Policy does not receive or transform candidate state values.
  • Policy operates before and after pipeline computation, not within it.
  • Policy decisions govern execution authority, not value shaping.
  • Policy controllers are evaluated collectively rather than sequentially.

This separation ensures that pipeline computation remains deterministic and that execution authority remains centralized, explicit, and serializable.

Common Policy Use Cases

  • Rate limiting or throttling execution attempts
  • Retrying failed attempts under controlled conditions
  • Pausing execution during external error states
  • Coordinating execution with external system readiness
2. Pre-Processing Layer

The Pre-Processing Layer executes before any state transformation occurs. This layer determines whether the pipeline should execute, when execution should occur, and whether an incoming update can be satisfied without entering the processing stages.

Unlike Controllers, which govern overall execution permission, pre-processing behaviors participate directly in the pipeline and operate on incoming updates prior to computation.

Responsibilities

  • Schedule and sequence pipeline execution
  • Delay, debounce, or suppress incoming updates
  • Short-circuit execution when cached or resolved values are available

Behaviors

Stage Purpose
Queue Controls execution ordering and scheduling for synchronous and asynchronous updates. Ensures updates enter the pipeline in a deterministic sequence.
Interceptors Applies timing-based controls such as delay, debounce, or throttling. Interceptors may suppress or defer updates before computation begins.
PreCache Evaluates cached or previously resolved values and may satisfy the update without executing the remaining pipeline stages.

By resolving scheduling, timing, and cache-based decisions early, the Pre-Processing Layer reduces unnecessary computation and ensures that only eligible updates proceed to state transformation.

3. Processing Layer

The Processing Layer is responsible for producing the next immutable state value for a FeatureCell. All state computation, transformation, validation, and reduction occurs within this layer.

Each behavior in this layer operates on the resolved input and the current state, progressively shaping the value that will become the next emitted snapshot.

Responsibilities

  • Normalize incoming input into a predictable value shape
  • Combine incoming values with existing state
  • Apply transformation, validation, and refinement rules
  • Produce a finalized, immutable state value

Behaviors

Stage Purpose
Resolve Normalizes incoming inputs into a consistent value shape. Ensures the processing pipeline begins with a predictable <T> value regardless of input source.
Merge Combines the resolved incoming value with the current state using the configured merge strategy. Merge behavior is extensible; replace semantics perform a full overwrite.
Operators Applies refinement logic such as deduplication, mapping, or suppression. Operators may transform or suppress values before reduction.
Filters Filters invoke engineer-supplied callback functions that examine the candidate next value and may remove, neutralize, or terminate its contribution to the upcoming state snapshot. Filters operate exclusively on the incoming value, preserve the structural shape of <T>, and influence what is applied—not whether the pipeline executes.
BeforeTap Executes engineer-supplied inspection or monitoring callbacks against the candidate next value prior to reduction. These callbacks are used strictly for observation and diagnostics and do not influence the computed state.
Reducers Reducers invoke engineer-supplied pure transformation callbacks that operate on the candidate next value to produce the final value for the next state snapshot. Reducers return a new value and do not mutate the existing in-memory state.
AfterTap Executes callbacks after the final state value has been produced. Used for logging, metrics, or side-effect observation.
Final State The completed, immutable value resulting from all processing behaviors. This value becomes the next emitted snapshot.

The Processing Layer defines the authoritative transformation boundary for FeatureCell state. All subsequent pipeline stages operate on the finalized output produced here.

4. Output Layer

The Output Layer runs after the Processing Layer has produced the final immutable state value. Its responsibility is to prepare that value for durability or transport without altering the in-memory state held by the FeatureCell.

Responsibilities

  • Prepare finalized state for external storage
  • Persist state to durable storage or external targets

Behaviors

Stage Purpose
Encrypt Produces an encrypted representation of the finalized state prior to persistence. Ensures sensitive data is not written to storage in plaintext form.
Persist Writes the finalized (and optionally encrypted) state to durable storage or a user-defined persistence target.

These behaviors operate strictly on the output of the processing pipeline. They do not participate in state transformation, validation, or computation.

Output behaviors do not modify the FeatureCell’s in-memory state. The FeatureCell always retains and exposes the plain, unencrypted final value. Encryption and persistence exist solely to produce external side effects and therefore do not influence subsequent pipeline stages.

5. Post-Processing Layer

The Post-Processing Layer executes after the pipeline has produced its final, immutable state snapshot. Behaviors in this layer observe, emit, or record the completed output without influencing state computation.

Roles

  • Emit finalized state snapshots to engineer-defined callbacks
  • Update caches derived from successful computation
  • Coordinate offline write tracking and replay

Behaviors

Stage Purpose
State Emitters Emits the completed StateSnapshotShape to engineer-supplied callback functions. It delivers the final snapshot without transforming or mutating state.
Post-Cache Records list or item results to cache after a successful state update has been computed.
Offline Mode Tracks offline writes, queues updates for later replay, or resolves by value while offline.

Why this layer is separate from processing

  • Behaviors require the final computed state snapshot.
  • They do not participate in transformation or validation.
  • They emit or record state rather than compute it.

State emitters are a delivery mechanism, not a computation stage. They guarantee that every finalized StateSnapshotShape is consistently surfaced to external observers while preserving pipeline determinism. State emission callbacks are secondary to the primary state observable and exist as an optional convenience for engineers who prefer imperative notification over subscription.

Post-processing behaviors are observational and coordinative in nature. They operate on completed output and never feed results back into the FeatureCell’s in-memory state.

6. Error Handling

Error handling in is orthogonal to the pipeline stages and applies uniformly across all layers. Errors do not alter computed state values. Instead, they are captured, normalized, optionally transformed, and attached to the next emitted StateSnapshotShape.

An error may originate from any pipeline layer, including controllers, pre-processing, processing, output, or post-processing. Regardless of origin, all errors are routed through the same structured error-handling sequence.

Error Handling Categories

  • Core Error Handling — guaranteed normalization and attachment of errors to the state snapshot.
  • Extendable Error Behaviors — optional transformation of normalized errors into engineer-defined shapes.
  • Error Emitters — optional callbacks for observing finalized error snapshots.

Core Error Handling

Core error handling is always present and executes regardless of which behaviors are enabled. It normalizes any thrown value into a VaultErrorShape and ensures the error is committed to the FeatureCell’s next StateSnapshotShape.

Core error handling does not modify the current or next state value. It updates error and loading fields only, ensuring state remains structurally consistent and observable even in failure scenarios.

Extendable Error Behaviors

After core error normalization, optional error behaviors may execute. These behaviors are engineer-defined callback functions that receive the normalized error and may return a new error shape. Each behavior runs independently and may refine, annotate, or replace the error representation that will be attached to the next state snapshot.

Error behaviors operate exclusively on the VaultErrorShape object associated with the upcoming StateSnapshotShape. They do not influence pipeline execution, state computation, scheduling, or control flow. Their sole responsibility is to shape the error representation exposed to consumers.

Error Emitters

Error emitters provide an optional, engineer-defined callback mechanism for observing finalized error snapshots. These callbacks receive the completed StateSnapshotShape after the error has been committed to state.

Error emitters are a delivery mechanism, not a computation stage. They are secondary to the primary state observable and exist as a convenience for engineers who prefer imperative notification in addition to reactive consumption. They do not alter state, error shape, or pipeline behavior.

In short: error behaviors shape the VaultErrorShape object; error emitters observe the finalized error snapshot.

Key Guarantees

  • Errors never mutate or replace computed state values.
  • Errors are always attached to a StateSnapshotShape.
  • Error normalization always occurs, even if custom behaviors fail.
  • Error handling does not interrupt pipeline determinism.
