How to build an Add-on

A Behavior is a composable, stage-bound unit of responsibility within the pipeline. Each Behavior performs a single, well-defined function, such as resolving input, filtering values, reducing state, observing snapshots, handling errors, or persisting output.

Behaviors are executed in a strict, predefined order based on their assigned pipeline stage. Each Behavior is aware of when it is permitted to run and what it is allowed to operate on. Some Behaviors transform candidate values, some observe finalized snapshots, and others perform side-effect work such as caching, persistence, or notification.

Behaviors are never implicitly enabled. A Behavior participates in a FeatureCell pipeline only if it is explicitly registered during FeatureCell configuration or is part of the minimal core pipeline provided by . If a Behavior is not registered, it is not executed.

When a FeatureCell is configured, validates each registered Behavior and inserts it into the correct pipeline stage. Ordering, execution boundaries, and stage isolation are enforced automatically. Behaviors do not discover or invoke one another directly.

This model allows FeatureCells to be assembled from small, focused units rather than relying on monolithic configuration or implicit control flow. Each Behavior exposes a clear contract and is responsible for exactly one concern.

Core Behaviors—such as Queue, Resolve, default Merge, and core error handling— are always present and ensure correct scheduling, input normalization, and immutable state snapshots. All other Behaviors are optional extensions that are enabled only when explicitly included.

Behavior Anatomy

Every Behavior conforms to a common contract so it can be executed safely and predictably within the pipeline:

  • A type that determines the pipeline stage in which the Behavior executes.
  • A unique key used for diagnostics, introspection, and tooling.
  • A critical designation indicating whether the Behavior is required for pipeline correctness.
  • A context object that provides access to the current snapshot and pipeline metadata relevant to that stage.
  • One or more stage-specific callbacks that perform the Behavior’s work.

Because all Behaviors follow this contract, they can be freely composed without awareness of one another. Each Behavior operates only on the inputs provided to its stage and returns a result or a no-op signal that allows the pipeline to continue unchanged.

Core vs Addon Behaviors

Behaviors fall into two categories: core and addon.

Core Behaviors

  • Built into and guaranteed for every FeatureCell.
  • Responsible for scheduling, input normalization, merge correctness, and error finalization.
  • Always present and cannot be omitted or reordered.

Addon Behaviors

  • Optional, engineer-selected Behaviors registered during FeatureCell configuration.
  • Addon Behaviors may be sourced from non-core packages (such as /addons) or implemented directly by engineers to address feature-specific or domain-specific requirements.
  • Provide capabilities such as filtering, operators, taps, caching, offline coordination, persistence, encryption, and error shaping.
  • Execute only within their declared pipeline stage and must respect all stage boundaries and contracts.

This separation ensures a stable, predictable core pipeline while allowing FeatureCells to be extended through explicitly declared, isolated behaviors.

Why Behaviors Matter

Behaviors define how FeatureCells remain modular, predictable, and extensible:

  • Composable — FeatureCell pipelines are assembled by listing Behaviors, not by configuring a monolithic store.
  • Deterministic — Each Behavior has a fixed stage, clear inputs, and bounded effects.
  • Extensible — Custom Behaviors can be introduced without modifying core.
  • Safe — Core Behaviors enforce invariants, while addon Behaviors are isolated to their declared responsibilities.

Understanding Behaviors is essential to understanding how FeatureCells are constructed and how state flows through the pipeline.

Pipeline

The Pipeline is the ordered lifecycle through which State is resolved and emitted. Each Stage is an execution slot occupied by a Behavior. Pipeline ordering is deterministic.
