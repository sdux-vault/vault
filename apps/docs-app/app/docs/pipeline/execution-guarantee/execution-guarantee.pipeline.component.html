Pipeline Execution Guarantees

Pipeline Execution Guarantees describes the execution model, ordering rules, and state commitment guarantees that underpin pipeline reliability.

This document explains how and when pipeline computation is executed, how asynchronous inputs are coordinated, and why state updates in are deterministic, atomic, and immune to common reentrancy and timing bugs.

These guarantees are not incidental. They are the result of deliberate architectural decisions that separate pipeline computation from state commitment and enforce strict execution boundaries.

This page is intended for advanced users, framework integrators, and engineers who want a precise mental model of execution semantics.

The Execution Model

executes state updates in two distinct phases: pipeline computation and state commitment.

Pipeline computation determines what the next state should be. State commitment determines when and how that result becomes visible to synchronous getters, reactive observers, callbacks, signals (in ), and DevTools.

These phases are intentionally separated and never interleaved. No state mutation, signal emission, or observer notification occurs until pipeline computation has completed successfully.

This separation is fundamental to ’s correctness guarantees.

Compute First, Commit Later

During pipeline execution, performs all of the following steps without mutating state:

  • Interceptor evaluation
  • Resolve behavior execution
  • Operator, filter, and reducer processing
  • Error normalization and transformation
  • Final state decision (commit, noop, stop, clear)

Only after the pipeline has fully determined a final outcome does proceed to state commitment.

This ensures that partial results, intermediate reducer output, and transient values are never observable outside the pipeline.

Microtask-Based State Commitment

Once pipeline computation completes, schedules state commitment using a microtask boundary.

State commitment—including signal updates, state callbacks, DevTools notifications, and controller notifications—is executed inside a queueMicrotask.

This guarantees that:

  • The current pipeline run completes fully before any observers are notified
  • No observer can trigger a new pipeline run while a commit is in progress
  • All observers see the same finalized snapshot

This design prevents reentrancy bugs, timing anomalies, and partial snapshot visibility that commonly affect asynchronous state systems.

Atomic Snapshot Guarantees

Every successful pipeline execution produces exactly one atomic snapshot.

That snapshot is:

  • Fully resolved
  • Fully filtered
  • Fully reduced
  • Fully normalized
  • Fully encrypted and persisted (if applicable)

Observers never see intermediate states, partially reduced values, or pre-normalized data. Either the entire snapshot is committed, or no state change is visible at all.

This atomicity applies equally to synchronous inputs, promises, observables, streams, and resource-backed values.

Reentrancy Is Structurally Impossible

prevents reentrant state updates by construction.

Because state commitment is deferred to a microtask, any attempt to trigger a new state update from within:

  • Reducers
  • State callbacks
  • DevTools hooks
  • Error handlers

will always occur after the current commit has completed.

This eliminates entire classes of bugs common in Redux-style systems, including:

  • Dispatching during reducer execution
  • Promise resolution interleaving with state writes
  • Observer-triggered infinite loops
Deterministic Ordering Across Async Boundaries

enforces a strict ordering model across synchronous code, promises, observables, and streams.

Regardless of how an input originates, the following ordering is guaranteed:

  1. Pipeline computation completes
  2. Final outcome is determined
  3. State commitment occurs in a microtask
  4. Observers are notified

This ordering is consistent across environments and does not depend on browser, Node.js, or event loop implementation details.

Why This Matters for Async Integrations

The execution guarantees described above are the foundation that allows to safely support:

  • Deferred promise factories
  • Observable resolution
  • Continuous stream ingestion
  • HTTP resource integration

By deferring commitment and enforcing lifecycle-aware resolution, ensures that asynchronous values cannot resolve outside of pipeline control or produce invalid state snapshots.

This is why strongly prefers deferred factories and pipeline-managed resolution over externally resolved promises or manually normalized values.

Execution Contract Summary
  • Pipeline computation is pure and side-effect free
  • State commitment is deferred and atomic
  • Reentrancy is structurally impossible
  • Async resolution is lifecycle-safe
  • Observers always see complete, consistent snapshots
  • Referential isolation is enforced at every stage boundary (Pipeline Isolation)

These guarantees are foundational. Every behavior, extension, and integration in is designed to preserve them.
