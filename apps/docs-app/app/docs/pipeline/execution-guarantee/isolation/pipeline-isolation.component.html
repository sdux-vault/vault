Pipeline Isolation

Pipeline Isolation describes the referential isolation contract that enforces at every pipeline boundary to prevent unintended mutations from propagating across stages.

This document explains what isolation means in the context of pipeline execution, how the isolation strategy works, and where isolation is applied across the pipeline lifecycle.

These guarantees are not incidental. They are the result of deliberate architectural decisions that ensure every pipeline stage operates on an independent copy of the data, eliminating mutation leaks by construction.

This page is intended for engineers who want a precise understanding of 's isolation boundaries, the types that receive full isolation, and the edge cases where JavaScript imposes inherent constraints.

The Isolation Strategy

enforces referential isolation at every pipeline boundary. All state values passed into and returned from pipeline stages are isolated automatically, preventing unintended mutations from propagating across stage boundaries.

The pipeline uses a clone-first, freeze-safe fallback strategy to guarantee deterministic structural isolation:

  • Primary: Deep cloning via structuredClone produces a fully independent copy of the value. This is the preferred path for plain objects, arrays, dates, typed arrays, and JSON-like data graphs.
  • Fallback: When deep cloning is not possible (for example functions, promises, or class instances), the pipeline applies a deep freeze or returns the value as-is, depending on the type. This prevents mutation where possible and preserves identity where cloning is not meaningful.

Primitives (number, string, boolean, bigint, symbol, null, undefined) are immutable by definition and are returned as-is without cloning.

Already-frozen objects are recognized as isolated and are returned without additional processing.

This separation between clone and freeze paths is fundamental to 's isolation contract.

Isolation Guarantees

The isolation strategy provides the following guarantees across the entire pipeline lifecycle:

  • No mutation leaks across pipeline boundaries
  • Stable, predictable data flow through all stages
  • Isolation is automatic and independent of user input shape
  • Cyclic object graphs are handled safely

These guarantees hold regardless of whether the pipeline processes synchronous values, promises, observables, or streams.

Isolation Limitations

JavaScript imposes inherent constraints on certain value types. The following are not guaranteed by pipeline isolation:

  • Prototype chain preservation on class instances
  • Custom properties on Error objects
  • Internal mutability of engine objects (Map, Set, Promise) when the fallback path is used
  • Non-enumerable and symbol-keyed property visibility

does not attempt to fight JavaScript's limitations. It constrains them deterministically, providing production-grade isolation for the vast majority of state shapes while remaining transparent about edge cases.

Recommended State Shapes

For maximum isolation guarantees, state values should be plain objects, arrays, primitives, dates, or JSON-serializable graphs. These value types receive full deep-clone isolation and are the ideal use case for pipeline state.

Avoid storing class instances, DOM nodes, observables, or WeakMap/WeakSet values in pipeline state. These types cannot be fully isolated and may produce unexpected behavior across pipeline boundaries.

Where Isolation Is Applied

Isolation is applied automatically at every pipeline boundary where state values cross between stages. The following table documents the specific isolation points enforced by the Conductor and Orchestrator.

Pipeline Isolation Points
Pipeline Boundary What Is Isolated
Incoming State State input values are isolated when entering the pipeline to prevent consumer-side mutations from affecting pipeline execution.
Pipeline Options Options passed into pipeline operations are isolated to prevent shared configuration from being mutated during execution.
Interceptor Stage The incoming state is isolated before each Interceptor behavior executes, preventing interceptors from mutating the original incoming value.
Resolve Stage Resolve results are isolated after computation to prevent downstream stages from seeing unintended mutations.
Stepwise Stages Both the last snapshot value and the current candidate are isolated before each Stepwise evaluation (StepwiseResolve, StepwiseFilter, StepwiseReducer).
Merge Stage Both the current state and the partial update are isolated before the merge computation. The merge result is isolated before continuing downstream.
Filter Stage The current state is isolated before each filter function executes. Filter results are isolated before continuing downstream.
Reducer Stage The current state is isolated before each reducer function executes. Reducer results are isolated before continuing downstream.
BeforeTap / AfterTap Observation stages receive isolated copies, ensuring that tap callbacks cannot corrupt pipeline data flow.
Final State The resolved state is isolated after reduction and before committing to the output layer.
Error Handling Error values, current state, and snapshots are all isolated before being passed to error transform behaviors and error callbacks.
Global Error Service The finalized error state is isolated before being committed to the global error service.
Isolation Contract Summary
  • Every pipeline stage operates on an isolated copy of the data
  • Isolation uses clone-first with a freeze-safe fallback for non-cloneable types
  • Isolation is automatic and requires no manual cloning by engineers
  • JSON-serializable state shapes receive full deep-clone isolation
  • Edge cases are constrained deterministically, not silently ignored

These guarantees are foundational. Every behavior, extension, and integration in is designed to preserve them.
