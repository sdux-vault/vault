Conductor Queue

The Conductor Queue serializes all pipeline attempts through a FIFO queue, guaranteeing that every state transition processed by a executes one at a time, in the exact order it was received.

The queue is the first stage in the policy layer. It establishes deterministic ordering before any controller evaluation, decision engine resolution, or pipeline computation begins.

This page describes the queue's responsibility boundaries, its relationship to the conductor, and the guarantees it provides to all downstream pipeline stages.

Queue Responsibility
↑ top

The queue is responsible for serializing pipeline attempts within a single . Every call to replace or merge state, and every initialization request, enters the queue before any other pipeline stage executes.

The queue does not evaluate, transform, or filter incoming attempts. Its sole responsibility is ordering. It receives attempts, holds them in sequence, and releases them one at a time for controller evaluation and pipeline execution.

Responsibility Description
Serialization all pipeline attempts are enqueued in arrival order and processed sequentially.
Ordering attempts execute in strict FIFO order — no attempt may bypass or preempt another.
Isolation only one attempt is active at any time — subsequent attempts remain queued until the active attempt finalizes.
FIFO Ordering Guarantee
↑ top

The queue enforces first-in, first-out ordering for all pipeline attempts. When multiple state updates are requested against the same , the queue guarantees that they execute in the exact order they were received.

This guarantee holds regardless of whether attempts are synchronous or asynchronous, and regardless of whether a controller denies, abstains, or allows the active attempt.

The FIFO guarantee eliminates race conditions, out-of-order state commits, and timing-dependent behavior that arise in systems without serialized execution.

Single Active Attempt
↑ top

The queue permits exactly one active pipeline attempt at a time. The active attempt is always the head of the queue. All other queued attempts remain pending until the active attempt completes its full lifecycle — from controller evaluation through pipeline execution to finalization.

When the active attempt finalizes, it is removed from the queue, and the next pending attempt (if any) becomes active. This progression is automatic and deterministic.

The single-active-attempt constraint ensures that no two pipeline executions overlap within a . Every pipeline stage — controllers, interceptors, resolve, merge, operators, filters, reducers, state, and extensions — operates on a stable, uncontested state foundation.

Microtask-Based Finalization
↑ top

When the active attempt completes, finalization occurs inside a microtask boundary. This ensures that the current pipeline cycle fully drains before the queue advances to the next attempt.

The finalization sequence within the microtask follows a fixed order:

Order Step Purpose
1 notify finalize signals the decision engine that the active attempt has completed.
2 remove from queue the finalized attempt is removed from the head of the queue.
3 reset processing flag the queue is marked as idle, ready to accept the next attempt.
4 signal settled emits a settled signal for devMode testing determinism.
5 process next attempt if pending attempts exist, the next one becomes active.

This ordering is non-negotiable — no step may be reordered, skipped, or split across multiple microtasks.

Reentrancy Immunity
↑ top

The queue's single-active-attempt constraint and microtask-based finalization together provide complete reentrancy immunity.

If a pipeline stage, controller, or observer triggers a new state update during execution of the active attempt, that update is enqueued — not executed immediately. It will be processed only after the current attempt finalizes.

This eliminates an entire category of bugs: double-finalization, out-of-order queue mutation, and re-entrant pipeline execution.

Tab sync is a real-world example. When multiple browser tabs share the same , the tab sync controller coordinates initial state negotiation across tabs using a BroadcastChannel. A newly opened tab sends a snapshot request to its peers. If a peer responds with a snapshot before the negotiation timeout, the controller aborts the initial attempt and commits the cached snapshot instead. If no peer responds, the controller abstains and the attempt proceeds normally.

During this negotiation window, any state updates triggered by the application — or by the snapshot commit itself — are enqueued rather than executed immediately. The queue guarantees that the negotiation attempt finalizes completely before the next queued attempt begins. Even the brief settling phase that follows a successful sync is protected: attempts arriving during settling are aborted and re-queued, preventing race conditions between the synced snapshot and in-flight local state.

Queue Lifecycle
↑ top

The queue is created when the conductor is instantiated for a . It persists for the lifetime of that .

When a is reset, the queue is drained and the processing flag is cleared. All pending attempts are discarded.

When a is destroyed, the queue is drained, the processing flag is cleared, and no further attempts are accepted.
